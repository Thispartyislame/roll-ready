# Architecture note

## Stack

**Electron + SQLite (Node's built-in `node:sqlite`) + Preact, with no build step.**

| Requirement | How this stack meets it |
|---|---|
| Fast local search/filter | The whole dataset (a campaign plus ~1,900 reference entries) is loaded into memory at launch (~10 ms). Every list, filter and lookup is an in-memory scan, so nothing waits on disk or IPC while you type. |
| Simple local storage | One SQLite file. `node:sqlite` ships inside Electron's Node, so there are **no native modules** to compile or rebuild per platform — `npm install && npm start` works the same on Windows and macOS. |
| Dense UI, quickly | Plain HTML/CSS with Preact + htm (one vendored 13 KB file). No bundler, no transpiler: the source you read is the source that runs. |

**Why not Tauri?** Smaller binaries and lower memory, but it adds a Rust toolchain and a second
language for the data layer, and its SQLite path needs a compiled plugin. For a single-user tool
whose bottleneck is never CPU, the simpler toolchain won. The cost is installer size (~100 MB).
The renderer only talks to the data layer through one narrow function (`dm.call(method, …args)`),
so moving to Tauri later means rewriting `main.js`/`src/db.js`, not the UI.

## Layout

```
main.js              Electron main process: GM window, player window, IPC endpoint, opens the DB
preload.js           GM window: dm.call(method, ...args) and dm.onPlayerStatus(cb)
preload-player.js    Player window: read the public state, toggle full screen, switch theme. Nothing else.
src/schema.js        Migrations (append-only list; PRAGMA user_version tracks progress)
src/db.js            Data layer: entity registry, load/save/remove, SRD and generator seeding
data/srd.json        Bundled SRD 5.2 content (generated by tools/build-srd.py)
data/generators.json Built-in generator tables (original content)
renderer/
  index.html, styles.css          GM window
  player.html, player.css         Player window
  js/player.js       Player view (plain DOM, no framework)
  js/lib.js          In-memory store, autosave, routing, markdown, @-mentions, pins, encounter maths
  js/components.js   Shared inputs: bound fields, type-to-search picker, link chips
  js/world.js        NPCs, locations, factions, quests, encounter builder, party
  js/sessions.js     Sessions, note log, @-mention note input, note search
  js/combat.js       Initiative rules and state (turn order, HP, rounds, publicState) — no UI
  js/tracker.js      Initiative tracker screen, player-view menu, end-combat dialog, pinned panels
  js/dice.js         Dice expression parser, roll history, quick-roll bar, roller panel
  js/timers.js       Countdown timers (seconds or rounds)
  js/monsters.js     Rollable stat block, homebrew monster editor, monster library
  js/lookup.js       Rules/spell/item lookup, SRD-gap messages, custom entries
```

No new libraries were added in Phase 2.

## Data flow

- **Read:** `bootstrap()` returns the shared library and settings; `loadCampaign(id)` returns every
  entity in that campaign with its links attached as id arrays (`npc.faction_ids`, `quest.npc_ids`…).
- **Write:** edits change the in-memory object immediately and are saved ~300 ms after the last
  keystroke (and on window blur/close). `save(type, obj)` writes the row and its join tables in one
  transaction. Deletes rely on `ON DELETE CASCADE` / `SET NULL`, then the campaign is reloaded.
- **Security:** context isolation on, node integration off, strict CSP, no remote content.

## Storage

SQLite in WAL mode with foreign keys on. Tables: `campaign`, `npc`, `location`, `faction`, `quest`,
`session`, `note`, `encounter` (campaign-scoped); `monster`, `spell`, `item`, `rule`, `condition`
(shared across campaigns); join tables `npc_faction`, `quest_npc`, `quest_location`, `note_npc`,
`note_quest`, `encounter_monster` (with quantity), `encounter_npc`, `session_encounter`; plus
`dice_log` and a small `kv` table for app state (live initiative tracker per campaign, active
session, window positions, pins, emergency-NPC history). Phase 2 (schema v2) adds `party_member` and
`timer` (campaign-scoped), `difficulty_threshold` and `gen_table` (shared), gives `encounter_monster`
its own id with `custom_name` / `hp_override`, and adds `campaign.party_level` / `party_size`,
`encounter.hp_mode`, and `dice_log.session_id` / `combatant`.

**Default chosen: SQLite over flat files.** It gives real relations and cascading deletes for the
"everything links to everything" requirement, atomic writes, and a single file to back up.
The trade-off is that the data isn't hand-editable or diff-friendly the way Markdown/JSON files
would be. If that matters later, an export to files is a small addition; the reverse is not.

Notes on the model:

- `campaign.system` is free text (new campaigns get "5E (2024 rules)"); nothing in the schema assumes 2024.
- Library tables have `source` ('SRD' or 'Homebrew') and a unique `srd_key`. SRD rows are upserted
  by key when the bundled data version changes, so updates never break encounter links or touch
  user entries. SRD rows are read-only at the data layer.
- Monster stat blocks are stored as JSON in the 2024 layout, with name/CR/type/AC/HP/initiative
  duplicated into columns for listing.
- Notes store mentions inline as `@[Name](npc:12)` and mirror them into `note_npc`/`note_quest`,
  so links survive renames and are searchable.
- Additions beyond the original brief, made for the "prep NPCs and drop them into initiative"
  request: optional `ac` / `max_hp` / `init_bonus` / `monster_id` on NPCs, and `encounter_npc`.

## Phase 2 decisions

**Player view: a second window, not a server.** `main.js` opens a second `BrowserWindow` with its own
preload (`preload-player.js`). The GM window builds a sanitized snapshot in one place —
`publicState()` in `combat.js` — and sends it through `playerPush`; the main process keeps the last
snapshot and relays it. That snapshot is the *only* thing the player window ever receives: name,
initiative, PC flag, active, down, an optional coarse health word, and condition names. Hidden
combatants are left out before the data leaves the GM window; HP numbers, AC, notes and stat blocks
are never in it. The player window cannot call the data API (the main process rejects `api` calls
from any window but the GM's). Window bounds, display and full-screen state are remembered; if the
saved display is gone it opens centred on the primary display. Nothing listens on the network.

**Encounter difficulty thresholds.** The Phase 2 brief said not to assume the XP budget table is
open content. What was found: the "XP Budget per Character" table (levels 1–20; Low / Moderate /
High) **is** in SRD 5.2, under Gameplay Toolbox → Combat Encounters, in the markdown conversion of
the SRD used to build `data/srd.json`, and SRD mirrors agree. It was **not** checked against the
official PDF. Decision: ship it as *editable defaults* in `difficulty_threshold`, seeded once from
`srd.json` (`xp_budget`) and never overwritten, with a grid in Settings to change any cell. If the
table turns out not to be covered, deleting `xp_budget` from the bundled data leaves a working
builder with an empty, GM-filled table. Monster XP by CR comes from the SRD stat blocks.

**Combat state persistence.** The tracker is one JSON record per campaign in `kv`
(`tracker:<campaign id>`), written ~120 ms after any change, so a crash mid-fight loses nothing.
Timers are rows in `timer`; a real-time timer stores `remaining` + `started_at`, so it keeps
counting correctly across a restart.

**Round timers flag, never remove.** An expired timer turns red and says EXPIRED until the GM
clears it. (Open question from the brief; flagging was the stated default.)

**Generators.** Every table is a `gen_table` row; built-in tables are seeded once per key and never
overwritten, so GM edits stick. The emergency NPC generator reads its options from the tables
themselves by key prefix (`enpc_occupation_<setting>`, `enpc_hook_<attitude>`, `npc_name_<style>`),
so a GM-added table becomes a new filter option. `generateNpc()` returns a plain object of named
fields — the seam where Phase 3 could put a different source.

## Open questions for the user

- Should the player view later reach players' own devices over the local network? This build is a
  second window only.
- The XP budget table: confirm against the official SRD 5.2 PDF (see above).
- Round timers flag rather than auto-remove — say if you'd prefer removal.

## Room for Phase 3 (AI-assisted generation)

Nothing is implemented, but the shape allows it: every entity is a plain row created through the
same `save(type, obj)` call the UI uses, `source` already distinguishes origin (a third value such
as 'Generated' needs no migration), and the single IPC endpoint is the natural place to add a
generation service without the renderer changing.

## Tested

Phase 2 was driven end to end under Electron 45 on Linux with an automated script (85 checks, no
console errors): party, monster filters and homebrew, encounter builder and difficulty, run
encounter, tracker keys, conditions, concentration prompt, timers (rounds and seconds), turn
reminders, player view (content, hidden combatants, live updates, theme, idle fade, close/reopen),
end-combat log, dice parser and history, lookup pins and SRD-gap path, every generator table,
emergency NPC (locks, filters, history, save), command palette actions, shortcut overlay, threshold
editing, and persistence across a restart. A Phase 1 database (schema v1 with world data, an
encounter and a live tracker) was upgraded in place and checked.

**Not tested:** Windows and macOS (no platform-specific code paths, but the player window's
multi-display behaviour, full screen and the installers need a smoke test on each); more than one
physical display ("Send to display…" was only exercised with a single display); a database produced
by the actual released Phase 1 build (the upgrade test used a database built from the v1 schema).
